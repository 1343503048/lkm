## 一、重要补丁系列（Patch Series）

### 1. sched_ext：限制 per-task 重入队并驱逐所属调度器 — v3 **已合入** ✅🔥
- **作者**：Tejun Heo `<tj@kernel.org>`；评审 Andrea Righi `<arighi@nvidia.com>`
- **邮件**：UID 1270（对 v2 意见的回复）、1271（v3 补丁）、1307（Andrea Reviewed-by）、1345（Tejun 宣布 Applied）
- **关联**：这是 7/26 记录的 v1/v2 系列（UID 476/483/770）的直接延续与收尾。
- **问题**：cap 拒绝没有重复上限，故障 BPF 调度器会把任务在 reject/reenqueue 间无限循环；reenqueue 的 `irq_work` 会自我重排且优先级高于 timer 向量，阻塞包括 stall 检测在内的一切，直到 NMI hardlockup 才触发。原有 `SCX_REENQ_LOCAL_MAX_REPEAT` 只覆盖 local DSQ，且按 per-cpu-on-root 计数存在**归因错误**——子调度器闯的祸会拆掉整个层级。
- **方案**：改用单一 per-task 计数器 `reenq_cnt`——在 `scx_do_enqueue_task()` 每次 `SCX_ENQ_REENQ` 递增（所有重入队生产者的唯一必经路径），在 `clr_task_runnable()`（任务被选中运行）与 `scx_disable_task()`（离开调度器控制）时清零；超过 `SCX_REENQ_MAX_REPEAT`（=256）即以新错误码 `SCX_EXIT_ERROR_REENQ` 驱逐所属调度器并将任务搁置到 sched exit 处理。事件 `SCX_EV_REENQ_LOCAL_REPEAT` → `SCX_EV_REENQ_REPEAT`，覆盖所有来源。删除了 `scx_rq` 上的 `deferred_reenq_locals_seq` 与 `scx_deferred_reenq_local` 里的 `seq/cnt` 冗余状态。
- **版本演进**：
  - v2：仅在"一次重入队又导致下一次重入队"时才计数 `SCX_EV_REENQ_REPEAT`（非每次都记）。
  - v3：（回应 Andrea）① 在 `scx_disable_task()` 也清零 `reenq_cnt`，避免计数跨调度类切换/调度器替换/子调度器 rehome 时残留导致新 owner 被误驱逐；② 修正 `sched-ext.rst` 中残留的 `SCX_EV_REENQ_LOCAL_REPEAT` 文档引用。
- **Maintainer 意见**：Andrea 曾质疑"是否只该限制内核驱动的 `SCX_TASK_REENQ_IMMED`/`SCX_TASK_REENQ_CAP` 而非所有重入队"，Tejun 明确回复"任务被重入队上百次而不运行本身就说明出错，对所有来源限制是合理的"。Andrea 最终给出 **Reviewed-by**，仅遗留一个小 nit：`enum_defs.autogen.h` 仍定义旧的 `HAVE_SCX_REENQ_LOCAL_MAX_REPEAT`——由下一个补丁处理（见 #2）。
- **合入评估**：**已 Applied 到 `sched_ext/for-7.3`**，附 Andrea 的 Reviewed-by。收敛完成。

### 3. sched/cache：修复单 runnable 任务下的线程聚合冲突（ITMT/asym-packing）
- **作者**：Chen Yu `<yu.c.chen@intel.com>`；Reported-by Yi Lai；评审 Zhan Xusheng
- **邮件**：UID 1487（补丁）、1730（Zhan Xusheng review）
- **问题**：在 PKG 域设了 `SD_ASYM_PACKING`（如启用 ITMT）的系统上，`sched_balance_find_src_rq()` 里的 `sched_asym()` 检查会阻止把单个任务从高优先级 CPU 拉到低优先级 CPU。这导致 `migrate_llc_task` 类型的缓存感知迁移失效——任务想迁到其偏好 LLC 以获得缓存局部性，却因 `sched_asym(PKG, cpu=0, dst=120) && nr_running==1` 被永久卡在错误 LLC。
- **方案**：对 `migrate_llc_task` 迁移类型豁免该 `sched_asym` 过滤（缓存局部性优先于 asym 优先级）。
- **Fixes**：`e4c9a4cb244a ("sched/cache: Add migrate_llc_task migration type for cache-aware balancing")`
- **Review 焦点**：Zhan Xusheng 认可修复方向，并自行论证**不会引入 asym-packing 与 migrate_llc_task 的乒乓迁移**（任务落到偏好 LLC 后，反向 asym 拉回属 `migrate_task`，会经 `can_migrate_llc_task()` 返回 `mig_forbid` 而被拦下，除非触发 `nr_balance_failed` 逃逸）。提出一个一致性疑问：紧邻的 `SD_ASYM_CPUCAPACITY` 单任务过滤同样是 `nr_running==1` 形态却未豁免 `migrate_llc_task`——认为当前硬件不可达（需同时多 LLC + 该域非对称算力），建议在 changelog 补一句说明意图（是有意让算力优先于缓存局部性，还是仅超出本补丁范围）。
- **合入评估**：单补丁 fix，方向获初步认可，暂无 NAK；预计作者补充 changelog 说明后可进入 tip。当前 `unknown` 是否已被 maintainer 拾取。

### 4. sched/cache：降低 task_cache_work 开销（只扫已访问 CPU）— v8 review + Tested-by

- **邮件**：UID 1465（Chen Yu 对 v8 1/2 的回复）

- **效果数据**：Chen Yu 在 Intel Sapphire Rapids（内存交织）与 AMD Milan（EPYC 9554P 64C）跑 hackbench：SPR 上无明显差异；Milan 上开启 NUMA balancing 时**有轻微回退，但落在 run-to-run 方差内**（附完整对比表，多数条目在 ±3% 抖动区间，个别 ±20%+ 明确标注为方差）。给出 **Tested-by: Chen Yu**，请作者在其 AMD 服务器复核回退是否为方差。

### 5. sched/psi：修复 32 位架构上 trigger 时间换算溢出 — **Acked** ✅
- **作者**：Guopeng Zhang `<zhangguopeng@kylinos.cn>`；Acked-by Suren Baghdasaryan
- **邮件**：UID 1580（Suren 的 Acked 回复，原补丁 7/17 发出）
- **问题**：`threshold_us`/`window_us` 为 `u32`，`NSEC_PER_USEC` 为 `1000L`，在 32 位架构上乘法按 32 位无符号运算，赋给 `u64` 前就已回绕。示例：4,000,000us threshold 存为 4e9 ns 正确，但 6,000,000us window 回绕成 1,705,032,704 ns——window 竟短于 threshold，触发器不再监控预期的 4s/6s 窗口。
- **方案**：乘法前将两者强转 `(u64)`，用 64 位算术完成换算。
- **Fixes**：`0e94682b73bf ("psi: introduce psi monitor")`
- **合入评估**：小而清晰的正确性修复，已获维护者 **Acked-by: Suren Baghdasaryan**，可直接进入 tip/urgent 路径。
